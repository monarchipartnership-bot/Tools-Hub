Технічна документація: архітектура модуля звітності (шаблон для перевикористання)

Довідник з архітектури, розрахунків та патернів побудови внутрішнього інструменту звітності — узагальнено на основі реального впровадження, щоб можна було перевикористати в інших проєктах.

1. Загальна архітектура

Модуль звітності — набір самостійних статичних HTML-сторінок (по одній на кожну сторінку/дію), без збірки та бекенду в класичному розумінні. Кожна сторінка:

  • Один файл .html з інлайновими <style> та <script> — без окремих .js/.css файлів і без білд-кроку.
  • Підключається до Supabase напряму з браузера через публічний (без логіну) клієнт supabase-js v2.
  • Зберігає весь "звіт" одним jsonb-знімком (snapshot) у відповідній таблиці — не нормалізована реляційна модель, а документо-орієнтована.
  • Спільний дизайн (кольори, шрифти, шапка, бічне меню) копіюється між сторінками як CSS-блок, не виноситься в спільний файл — свідомий вибір для простоти деплою (кожен .html можна відкрити як окремий файл, без збірки).

1.1 Ієрархія звітності

Кожен рівень звітності будується на основі попереднього:

  • Тижневий звіт (Weekly) — базовий рівень, дані вводяться вручну.
  • Місячний звіт (Monthly) — автоматично підсумовує всі тижневі звіти цього місяця.
  • Річний звіт (Annual) — автоматично підсумовує всі місячні звіти цього року.
  • Денний звіт (Daily) — окремий, паралельний рівень (не підсумовується нікуди), для щоденного лога роботи.

Для кожного рівня (окрім денного) є до 3 сторінок-дій: Create (створення/перегляд поточного періоду з можливістю зберегти), Compare (порівняння кількох періодів поруч) та History (перегляд лише для читання будь-якого збереженого періоду).

2. Дизайн-система

Всі сторінки використовують один і той самий набір CSS custom properties (root variables) — тобто "токени" дизайну. Значення нижче — приклад з конкретної реалізації; для нового проєкту їх треба замінити на кольори власного бренду, сама структура токенів (фон/акцент/текст/статуси) — і є патерн, який варто перенести:

:root{
  --bg-1:#160616; --bg-2:#2a0a2a; --bg-3:#3a0f38;     /* фонові градієнти, від темного до світлішого */
  --accent-1:#E8C079; --accent-2:#C24BC2; --accent-3:#421342;   /* акцентні кольори бренду */
  --text:#f5eef5; --text-muted:#c2a6c2;              /* текст і другорядний текст */
  --line:rgba(255,255,255,.12);                      /* межі/розділювачі */
  --card:rgba(255,255,255,.045); --card-2:rgba(255,255,255,.02); /* фон карток */
  --ok:#4AE08A; --warn:#FCD34D; --bad:#FC8181;       /* статусні кольори: успіх/увага/помилка */
}

Шрифти: одна пара — жирний/заголовковий шрифт для лейблів і заголовків (у прикладі — Montserrat) + шрифт для основного тексту (у прикладі — Inter), підключені одним рядком через Google Fonts @import.

Спільні елементи, що повторюються на кожній сторінці:

  • Анімований фон — два розмитих кольорових "blob" з keyframe-анімацією, додає глибину фону без важких зображень.
  • Шапка (topbar) — липка (sticky), з логотипом (інлайновий SVG, підставляється через JS), кнопками "Назад" / експорт / "Зберегти".
  • Бічне меню (sidebar) — якорі на розділи сторінки (для довгих звітів), з кнопкою-бургером для згортання на мобільних.
  • Кнопка "Назад" завжди працює за принципом: history.length>1 ? history.back() : location.href='index.html' — щоб не губити користувача, якщо сторінку відкрили напряму, без історії переходів.

3. Backend: Supabase без логіну

Свідоме архітектурне рішення: внутрішній інструмент без користувацьких акаунтів. Клієнт створюється прямо в браузері з публічним (publishable) ключем:

var SUPA_URL = 'https://xxxx.supabase.co';
var SUPA_KEY = 'sb_publishable_xxxx';
var supa = window.supabase.createClient(SUPA_URL, SUPA_KEY);

Row Level Security увімкнено на кожній таблиці, але політики дозволяють всі дії (select/insert/update/delete) без перевірки автора — прийнятно лише для внутрішнього інструменту в довіреному середовищі, не для публічного продукту.

3.1 Таблиці (по одній на рівень звітності)

ТаблицяУнікальний ключПризначення data (jsonb)

Кожна таблиця має однакову "форму" колонок: id (uuid), author, data (jsonb), created_at, updated_at + свої "координатні" поля (year/month/week_index тощо) для фільтрації. Один запис на період — повторне збереження робить upsert по унікальному ключу (не створює дублікат).

SQL-схема ведеться в одному файлі, ідемпотентно (create table if not exists, alter table ... add column if not exists, drop policy if exists + recreate) — можна запускати повторно без помилок навіть якщо частина схеми вже існує.

4. Конфігурація показників — єдине джерело правди

Найважливіший патерн для перевикористання: усі метрики/конверсії/статті витрат описані як масиви конфігурації (не хардкод у розмітці), і рендеряться з них. Один і той самий "shape" ідентифікаторів повторюється на кожному рівні звітності (тиждень → місяць → рік) — це те, що дозволяє підсумовувати дані між рівнями напряму по id.

Приклад нижче — з конкретної реалізації для агентства перформанс-маркетингу (канали Upwork + LinkedIn); у своєму проєкті замініть на власні категорії показників, зберігши саму структуру:

var CHANNELS = [
  { key:'ch1', label:'Канал 1',
    metrics:[{id:'ch1_metric_a',label:'Показник A'}, {id:'ch1_metric_b',label:'Показник B'}, ...],
    ratios:[{id:'ch1_a2b',label:'A до B', num:'ch1_metric_b', den:'ch1_metric_a'}, ...]
  },
  // ...решта каналів
];
var COST_ITEMS = {
  category1: [ {id:'c1_item_n', label:'Стаття витрат', exp:true}, ... ],
  category2: [...]
};

Кожен елемент конфігурації породжує однакову картку (KPI-картку для метрики, картку з кільцевим індикатором для конверсії, рядок вартості для статті витрат) через одну й ту саму render-функцію — додати нову метрику означає додати один об'єкт у масив, а не правити розмітку в кількох місцях.

5. Формули розрахунку

Що рахуєтьсяФормула
Конверсія (ratio, %)pctVal(num, den) = den ? (num/den*100) : null
Вартість "непрямої" (count-based) статті витрат$ = кількість * RATE, де RATE — фіксований коефіцієнт переведення кількості дій у гроші
Вартість "прямої" (direct) статті витратзначення вже зберігається в грошах — береться як є, без множення на RATE (наприклад: підписки, комісії)
Знак витратиякщо стаття позначена як витрата → віднімається (від'ємне значення); якщо як повернення коштів → додається (додатне значення)
Загальний дохідсума доходу за всіма джерелами
Загальні витратисума всіх статей витрат за всіма категоріями — вже зі знаком
Прибутокзагальний дохід + загальні витрати (витрати вже від'ємні)

5.1 Принцип "спочатку сума, потім ділення" (sum-then-divide)

Це найважливіше архітектурне правило для агрегації по періодах. Коли місячний звіт підсумовує кілька тижневих, або річний підсумовує 12 місячних, конверсії (%) ніколи не усереднюються напряму. Натомість:

  1. Підсумовуються сирі числа (лічильники) по всіх періодах — окремо чисельник, окремо знаменник.
  2. Конверсія рахується один раз, з підсумованих чисел: pctVal(сума_num, сума_den).

Це усуває викривлення, коли період з малим обсягом даних (наприклад, тиждень із 2 лідами) мав би такий самий вплив на середнє, як і тиждень із 200 лідами. Той самий принцип застосовано і до фінансів — з кожного періоду підсумовуються сирі лічильники статей витрат, а вже потім рахуються гроші та прибуток.

6. Тижневий звіт (Weekly) — базовий рівень

  • Дані вводяться вручну по кожному каналу/джерелу лідів.
  • Прив'язка до конкретного тижня місяця обчислюється функцією, яка розбиває місяць на тижні (понеділок-неділя), обрізаючи перший/останній тиждень межами місяця.
  • Зберігається з ключем "початок тижня"; поля рік/місяць/номер тижня — для фільтрації при підсумовуванні на місячному рівні.

7. Місячний звіт (Monthly) — автопідсумок з тижневих

  • Create: при виборі рік+місяць — вантажить усі тижневі звіти цього місяця, підсумовує всі показники (метрики + дохід + статті витрат), перераховує конверсії й фінанси, показує "Тижнів знайдено: X з Y" (скільки тижнів місяця реально знайдено в базі) — і зберігає готовий знімок у місячну таблицю. Розділ "Задачі" (план / виконано / плани далі / висновки) — єдине, що вводиться вручну на цьому рівні, не підсумовується.
  • Compare: дозволяє додати кілька довільних місяців (з будь-яких років) як "слоти" — і показує їх поряд у вигляді таблиць + барчартів по кожному блоку показників. Читає вже готовий знімок напряму з місячної таблиці (не перераховує заново).
  • History: режим лише перегляду — вибираєш рік+місяць, бачиш збережений звіт як є, без можливості редагувати.

8. Річний звіт (Annual) — автопідсумок з місячних

Побудований за такою ж логікою, що й місячний, але на рівень вище:

  • Огляд місяців — сітка з 12 карток (по одній на кожен місяць року), кожна показує назву місяця, іконку сезону та кнопку "Детальніше", яка відкриває модальне вікно з повною деталізацією цього місяця (ті самі картки показників, що і на місячному рівні, але для одного місяця).
  • Річний підсумок — сума показників усіх знайдених місячних звітів року, і конверсія рахується з цих сум за принципом sum-then-divide.
  • Графіки за місяцями — по кожному блоку показників будується "діаграма з областю" (area/line chart): вісь X — 12 місяців, кожна лінія — окремий показник цього блоку; відсутні місяці показуються як розрив лінії, а не як нуль — щоб не спотворювати тренд.

Технічно ключова відмінність від місячного рівня: джерело агрегації — не сирі показники (як у тижневих звітах), а вже вкладений об'єкт підсумків (бо місячний звіт сам є "знімком" з підсумованими значеннями).

9. Compare-сторінки — механізм "слотів" і графіків

Спільний патерн для порівняльних сторінок будь-якого рівня:

  • Користувач додає періоди по одному через невелику панель — кожен доданий період стає "слотом" (зазвичай максимум 5-6).
  • Кожен блок показників рендериться однією функцією-білдером, яка одночасно будує: (а) таблицю з рядком на кожен показник і колонкою на кожен слот, підсвічуючи найкраще значення в рядку; (б) стовпчикову діаграму з тими самими даними.
  • Кожен блок — згортається/розгортається кнопкою, щоб довгий звіт не перевантажував сторінку.
  • Графіки перебудовуються при кожній зміні слотів: спершу знищуються всі активні графіки, потім будуються нові з черги — це запобігає витоку пам'яті/накопиченню canvas-контекстів при частій зміні вибірки.

Річний рівень повторно використовує саме цей механізм "згортання + перебудова графіків", але адаптований під один часовий ряд (12 місяців) з типом графіка "лінія з областю" замість стовпчикової діаграми.

10. History-сторінки — режим лише читання

Спільний патерн: вибираєш період із select — сторінка вантажить збережений рядок з відповідної таблиці по унікальному ключу і рендерить ті самі картки, що і Create-сторінка, але: без полів вводу (просто текст), без кнопки "Зберегти", задачі показуються як прості картки замість редагованих полів. Якщо запису немає — показується порожній стан ("За цей період звіт ще не збережено").

11. Приклад окремого інструменту поза базою даних

Крім самих звітів, у проєкті є самостійний Canvas-based генератор маркетингових зображень (не пов'язаний з базою даних звітів) — корисний приклад іншого типу інструменту в тому ж дизайні. Ключова архітектура:

  • Фіксований розмір canvas, малюється функціями з об'єкта конфігурації шаблонів — по одній функції на шаблон.
  • Кілька готових кольорових палітр — стосуються лише кольорів самого зображення, не інтерфейсу редактора.
  • Увесь стан (шаблон, палітра, кольори, тексти, завантажене фото) зберігається в localStorage і автоматично відновлюється при відкритті сторінки — без бекенду.
  • Експорт: малює той самий canvas у повній роздільній здатності в окремий offscreen-canvas, конвертує в PNG/JPEG, показує прев'ю в модальному вікні з кнопками завантаження.

12. Методологія тестування

Кожна сторінка перевіряється функціонально через jsdom (без реального браузера):

  • Клієнт бази даних підмінюється на мок-об'єкт з ланцюжковими методами (select/eq/maybeSingle/upsert), що повертає заздалегідь підготовлені тестові рядки.
  • Бібліотека графіків підмінюється легким "recording"-класом (записує конфігурацію замість реального малювання) — бо jsdom не має справжнього canvas-рендерера без нативного пакета canvas; це дозволяє перевірити, що в графік передані правильні labels/datasets, не малюючи піксель в піксель.
  • Перевіряються: коректність підрахунків (порівняння з очікуваним числом, порахованим окремо в тесті), правильна побудова/знищення графіків при перемиканні періоду (немає витоку), поведінка на межових випадках (0 показників, 1 показник, відсутній період, немає збереженого запису).

Відома пастка: файли, скопійовані з робочої теки у тестове тимчасове середовище, іноді містять зайві null-байти в кінці файлу (артефакт копіювання, не помилка самого файлу) — перед тестуванням варто програмно перевіряти файл і видаляти null-байти, інакше парсери можуть або впасти, або визначити файл як бінарний.

13. Чек-лист для перевикористання в інших проєктах

  1. Визначити ієрархію рівнів звітності (день → тиждень → місяць → рік або аналогічну) і яка таблиця/рівень підсумовує який.
  2. Описати всі показники/конверсії/статті витрат як конфігураційні масиви з id/label/num/den — одні й ті самі id повинні бути наскрізними через усі рівні.
  3. Один jsonb-стовпець "data" на таблицю замість окремих колонок під кожен показник — легко розширювати, не потребує міграцій при додаванні нової метрики.
  4. Уніфікувати ключ конфлікту (unique index) по "початку періоду" — це спрощує upsert "один запис на період".
  5. Дотримуватись правила "спочатку сума, потім ділення" для будь-яких відсоткових показників при агрегації періодів.
  6. Кожен рівень: 3 стандартні дії — Create (редагування+збереження), Compare (кілька слотів поруч + графіки), History (лише читання).
  7. Спільні CSS-токени (кольори/шрифти/шапка/бічне меню) копіювати як блок на початок кожної нової сторінки — простіше за спільний файл, якщо сторінки мають лишатись самостійними .html без збірки.
  8. Для графіків: один спільний "згортання + перебудова" білдер, який можна перевикористати і для порівняння (стовпчики), і для тренду в часі (лінія/область).
  9. Тестувати кожну сторінку через jsdom з мок-базою даних і мок-графіками перед здачею — особливо межові випадки (порожні дані, відсутній період).
