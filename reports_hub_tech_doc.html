Mon'Archi Tools Hub — технічна документація розділу Reports

Довідник з архітектури, розрахунків та патернів, які можна повторно використовувати в інших проєктах.

1. Загальна архітектура

Reports Hub — набір самостійних статичних HTML-сторінок (по одній на кожну сторінку/дію), без збірки та бекенду в класичному розумінні. Кожна сторінка:

  • Один файл .html з інлайновими <style> та <script> — без окремих .js/.css файлів і без білд-кроку.
  • Підключається до Supabase напряму з браузера через публічний (без логіну) клієнт supabase-js v2.
  • Зберігає весь "звіт" одним jsonb-знімком (snapshot) у відповідній таблиці — не нормалізована реляційна модель, а документо-орієнтована.
  • Спільний дизайн (кольори, шрифти, топбар, бічне меню) копіюється між сторінками як CSS-блок, не виноситься в спільний файл — свідомий вибір для простоти деплою (кожен .html можна відкрити як окремий файл, без збірки).

1.1 Ієрархія звітності

Кожен рівень звітності будується на основі попереднього:

  • Weekly Report — базовий рівень, дані вводяться вручну.
  • Monthly Report — автоматично підсумовує всі Weekly Reports цього місяця.
  • Annual Report — автоматично підсумовує всі Monthly Reports цього року.
  • Daily Report — окремий, паралельний рівень (не підсумовується нікуди), для щоденного лога роботи менеджера.

Для кожного рівня (окрім Daily) є до 3 сторінок-дій: Create (створення/перегляд поточного періоду з можливістю зберегти), Compare (порівняння кількох періодів поруч) та History (перегляд лише для читання будь-якого збереженого періоду).

2. Дизайн-система

Всі сторінки використовують один і той самий набір CSS custom properties (root variables) — це і є "бренд-токени" проєкту:

:root{
  --bgA:#160616; --bgB:#2a0a2a; --bgC:#3a0f38;      /* фонові градієнти (темний плам) */
  --gold:#E8C079; --mag:#C24BC2; --plum:#421342;     /* акцентні кольори бренду */
  --text:#f5eef5; --mut:#c2a6c2;                     /* текст і другорядний текст */
  --line:rgba(255,255,255,.12);                      /* межі/розділювачі */
  --card:rgba(255,255,255,.045); --card2:rgba(255,255,255,.02); /* фон карток */
  --ok:#4AE08A; --warn:#FCD34D; --bad:#FC8181;       /* статусні кольори (успіх/увага/помилка) */
}

Шрифти: Montserrat (заголовки, лейбли, uppercase-текст) + Inter (основний текст), підключені одним рядком через Google Fonts @import.

Спільні елементи, що повторюються на кожній сторінці:

  • .glow-wrap — анімований розмитий фон (два кольорових "blob" з keyframe-анімацією floatG1/floatG2), додає глибину фону без важких зображень.
  • .topbar — липка (sticky) шапка з логотипом (інлайновий SVG, підставляється через JS), кнопками Back / експорт / Save.
  • .sidebar — бічне меню з якорями на розділи сторінки (для довгих звітів), з бургер-кнопкою для згортання на мобільних.
  • Кнопка "Back" завжди працює за принципом: history.length>1 ? history.back() : location.href='index.html' — щоб не губити користувача, якщо сторінку відкрили напряму.

3. Backend: Supabase (без логіну)

Свідоме архітектурне рішення: internal-tool без користувацьких акаунтів. Клієнт створюється прямо в браузері з публічним (publishable) ключем:

var SUPA_URL = 'https://xxxx.supabase.co';
var SUPA_KEY = 'sb_publishable_xxxx';
var supa = window.supabase.createClient(SUPA_URL, SUPA_KEY);

Row Level Security увімкнено на кожній таблиці, але політики дозволяють всі дії (select/insert/update/delete) без перевірки автора — прийнятно лише для внутрішнього інструменту в довіреному середовищі, не для публічного продукту.

Кожна таблиця має однакову "форму" колонок: id (uuid), author, data (jsonb), created_at, updated_at + свої "координатні" поля (year/month/week_index тощо) для фільтрації. Один запис на період — повторне збереження робить upsert по унікальному ключу (не створює дублікат).

SQL-схема ведеться в одному файлі supabase_setup.sql, ідемпотентно (create table if not exists, alter table ... add column if not exists, drop policy if exists + recreate) — можна запускати повторно без помилок навіть якщо частина схеми вже існує.

4. Конфігурація показників — єдине джерело правди

Найважливіший патерн для перевикористання: усі метрики/конверсії/статті витрат описані як масиви конфігурації (не хардкод у розмітці), і рендеряться з них. Один і той самий "shape" ідентифікаторів повторюється у Weekly → Monthly → Annual — це те, що дозволяє підсумовувати дані між рівнями напряму по id.

var CHANNELS = [
  { key:'mb', label:'Manual Bidding',
    metrics:[{id:'mb_cl',label:'Cover Letters'}, {id:'mb_a',label:'Answers'}, ...],
    ratios:[{id:'mb_c2a',label:'CL to Answers', num:'mb_a', den:'mb_cl'}, ...]
  },
  // ...ще 5 каналів (GetMany, Invites, Direct Message, Consultations, Project Catalog)
];
var LI_METRICS = [ {id:'li_conn', label:'Connections'}, ... ];
var LI_RATIOS  = [ {id:'li_c2l', label:'Connections to Leads', num:'li_leads', den:'li_conn'}, ... ];
var COST_ITEMS = {
  profiles: [ {id:'up_c_badge_n', label:'Availability badge', exp:true}, ... ],
  mb: [...], gm: [...], li: [...]
};

Кожен елемент конфігурації породжує однакову картку (KPI-картку для метрики, картку з кільцевим індикатором для конверсії, рядок вартості для cost item) через одну й ту саму render-функцію — додати нову метрику означає додати один об'єкт у масив, а не правити розмітку в 5 місцях.

5.1 Принцип "спочатку сума, потім ділення" (sum-then-divide)

Це найважливіше архітектурне правило для агрегації по періодах. Коли Monthly підсумовує 4-5 Weekly Reports, або Annual підсумовує 12 Monthly Reports, конверсії (%) ніколи не усереднюються напряму. Натомість:

  1. Підсумовуються сирі "Факт" числа (лічильники) по всіх періодах — окремо чисельник, окремо знаменник.
  2. Конверсія рахується один раз, з підсумованих чисел: pctVal(сума_num, сума_den).

Це усуває викривлення, коли період з малим обсягом даних (наприклад, тиждень із 2 лідами) мав би такий самий вплив на середнє, як і тиждень із 200 лідами. Той самий принцип застосовано і до фінансів — з кожного періоду підсумовуються сирі лічильники cost items, а вже потім рахується $ і profit.

6. Weekly Report — базовий рівень

  • Дані вводяться вручну по кожному з 6 каналів Upwork (Manual Bidding, GetMany, Invites, Direct Message, Consultations, Project Catalog) + LinkedIn.
  • Прив'язка до конкретного тижня місяця обчислюється функцією computeWeeksForMonth(year, month) — розбиває місяць на тижні (понеділок-неділя), обрізаючи перший/останній тиждень межами місяця.
  • Зберігається в weekly_reports з ключем week_start; поля year/month/week_index — для фільтрації при підсумовуванні в Monthly.

7. Monthly Report — автопідсумок з Weekly

  • Create (monthly.html): при виборі Рік+Місяць — вантажить усі weekly_reports з year=Y and month=M, підсумовує всі ALL_SUM_IDS (метрики + income + cost items) через computeSums(rows), перераховує ratioPct і фінанси, показує "Тижнів знайдено: X з Y" (скільки тижнів місяця реально знайдено в базі) — і зберігає готовий знімок (sums, ratioPct, finance, tasks, manager) у monthly_reports. Розділ "Задачі" (план/виконано/плани далі/висновки) — єдине, що вводиться вручну на цьому рівні, не підсумовується.
  • Compare (monthly_compare.html): дозволяє додати до 6 довільних місяців (з будь-яких років) як "слоти" — і показує їх поряд у вигляді таблиць + барчартів (Chart.js) по кожному блоку показників. Читає вже готовий знімок data.sums/data.ratioPct/data.finance з monthly_reports напряму (не перераховує).
  • History (monthly_history.html): режим лише перегляду — вибираєш Рік+Місяць, бачиш збережений звіт як є, без можливості редагувати.

8. Annual Report — автопідсумок з Monthly

Найновіший рівень, побудований за такою ж логікою, що й Monthly, але на рівень вище:

  • Огляд місяців — сітка з 12 карток (по одній на кожен місяць року), кожна показує назву місяця, іконку сезону (зима/весна/літо/осінь — грудень-лютий/березень-травень/червень-серпень/вересень-листопад) та кнопку "Детальніше", яка відкриває модальне вікно з повною деталізацією цього місяця (ті самі картки Upwork/LinkedIn/Фінанси + задачі, що і в Monthly, але для одного місяця).
  • Річний підсумок — сума показників усіх знайдених Monthly Reports року (читає monthly.data.sums, підсумовує), і конверсія рахується з цих сум за принципом sum-then-divide.
  • Графіки за місяцями — по кожному блоку показників (кожен Upwork-канал окремо, LinkedIn, кожна категорія витрат, підсумок) будується "діаграма з областю" (area/line chart, Chart.js): вісь X — 12 місяців, кожна лінія — окремий показник цього блоку; відсутні місяці показуються як розрив лінії (spanGaps:false), а не як нуль — щоб не спотворювати тренд.

Технічно ключова відмінність від Monthly: джерело агрегації — не сирі показники з data[id] (як у weekly_reports), а вкладені data.sums[id] (бо monthly_reports вже сам є "знімком" з підсумованими значеннями).

9. Compare-сторінки — механізм "слотів" і графіків

Спільний патерн для Weekly Compare і Monthly Compare:

  • Користувач додає періоди по одному через невелику панель (вибір року+місяця/тижня) — кожен доданий період стає "слотом" (максимум 6).
  • Кожен блок показників (наприклад, "Manual Bidding — Показники") рендериться функцією buildBlock(title, rowsMeta, formatFn, hlLabels), яка одночасно будує: (а) таблицю з рядком на кожен показник і колонкою на кожен слот, підсвічуючи найкраще значення в рядку; (б) стовпчикову діаграму Chart.js з тими самими даними.
  • Кожен блок — згортається/розгортається кнопкою (.collapse-btn + .cmp-collapsible), щоб довгий звіт не перевантажував сторінку.
  • Графіки перебудовуються при кожній зміні слотів через flushCharts(): спершу знищує (.destroy()) усі активні Chart-інстанси, потім будує нові з черги CHARTS_QUEUE — це запобігає витоку пам'яті/накопиченню canvas-контекстів при частій зміні вибірки.

Annual Report повторно використовує саме цей collapse-btn/cmp-collapsible/flushCharts механізм, але адаптований під один часовий ряд (12 місяців) з типом графіка line + fill:true (область) замість bar.

10. History-сторінки — режим лише читання

Спільний патерн: вибираєш період (рік/місяць/тиждень/день) із select — сторінка вантажить збережений рядок з відповідної таблиці по унікальному ключу і рендерить ті самі картки, що і Create-сторінка, але: без <input>/<textarea> (просто текст), без кнопки Save, задачі показуються як прості картки (.ro-item) замість редагованих полів. Якщо запису немає — показується порожній стан ("За цей період звіт ще не збережено").

11. Portfolio Studio — окремий інструмент (не звіт)

Самостійний Canvas-based генератор маркетингових зображень для Upwork Project Catalog/Portfolio (не пов'язаний з базою даних звітів). Ключова архітектура:

  • Фіксований canvas 1000×750px, малюється функціями з об'єкта DRAW — по одній функції на шаблон (наразі 10 шаблонів: Royal Editorial, Diagonal Split, Showcase, Big Type, Orbit, Glass Frame, Data Ledger, Twin Panel, Numeral Hero, Aurora Pill).
  • 3 готові кольорові палітри (PRESETS: royal/magenta/onyx) — стосуються лише кольорів самого зображення, не інтерфейсу редактора.
  • Увесь стан (шаблон, палітра, кольори, тексти, метрики, завантажене фото) зберігається в localStorage і автоматично відновлюється при відкритті сторінки — без бекенду.
  • Експорт: малює той самий canvas у повній роздільній здатності в окремий offscreen-canvas, конвертує в PNG/JPEG dataURL, показує прев'ю в модалці з кнопками "Завантажити" / "Відкрити в новій вкладці".

12. Методологія тестування

Кожна сторінка перевіряється функціонально через jsdom (без реального браузера):

  • Supabase-клієнт підмінюється на мок-об'єкт з ланцюжковими методами .from().select().eq().maybeSingle()/.upsert(), що повертає заздалегідь підготовлені тестові рядки.
  • Chart.js підмінюється легким "recording"-класом (записує config замість реального малювання) — бо jsdom не має справжнього canvas-рендерера без нативного пакета canvas; це дозволяє перевірити, що в графік передані правильні labels/datasets, не малюючи піксель в піксель.
  • Перевіряються: коректність підрахунків (порівняння з очікуваним числом, порахованим окремо в тесті), правильна побудова/знищення графіків при перемиканні періоду (немає витоку), поведінка на межових випадках (0 метрик, 1 метрика, відсутній період, немає збереженого запису).

Відома пастка: файли, скопійовані з робочої теки у тестове тимчасове середовище (bash-sandbox), іноді містять зайві null-байти в кінці файлу (артефакт копіювання, не помилка самого файлу) — перед тестуванням варто програмно перевіряти файл (data.count(b'\x00')) і видаляти null-байти, інакше jsdom/парсери можуть або впасти, або визначити файл як бінарний.

13. Чек-лист для повторного використання в інших проєктах

  1. Визначити ієрархію рівнів звітності (день→тиждень→місяць→рік або аналогічну) і яка таблиця/рівень підсумовує який.
  2. Описати всі показники/конверсії/статті витрат як конфігураційні масиви з id/label/num/den — одні й ті самі id повинні бути наскрізними через усі рівні.
  3. Один jsonb-стовпець "data" на таблицю замість окремих колонок під кожен показник — легко розширювати, не потребує міграцій при додаванні нової метрики.
  4. Уніфікувати ключ конфлікту (unique index) по "початку періоду" (week_start/month_start/year_start) — упрощує upsert "один запис на період".
  5. Дотримуватись правила "спочатку сума, потім ділення" для будь-яких відсоткових показників при агрегації періодів.
  6. Кожен рівень: 3 стандартні дії — Create (редагування+збереження), Compare (кілька слотів поруч + графіки), History (лише читання).
  7. Спільні CSS-токени (кольори/шрифти/topbar/sidebar) копіювати як блок на початок кожної нової сторінки — простіше за спільний файл, якщо сторінки мають лишатись самостійними .html без збірки.
  8. Для графіків: один спільний "collapsible block + Chart.js" білдер (buildBlock/flushCharts), який можна перевикористати і для порівняння (bar), і для тренду в часі (line/area).
  9. Тестувати кожну сторінку через jsdom з мок-Supabase і мок-Chart перед здачею — особливо межові випадки (порожні дані, відсутній період).
